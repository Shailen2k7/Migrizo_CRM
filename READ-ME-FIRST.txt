MIGRIZO — PHASE 2B: THE SEQUENCE ENGINE + 4-TAB WHATSAPP MODULE
================================================================

WHAT THIS IS
  WhatsApp is now a full module with four sub-tabs:

    Inbox      what you had, plus real Pause/Resume/Stop per lead
    Sequences  build automation as a numbered step list — pick a
               template, set "wait N days", drag to reorder, enrol
               a filtered batch, watch progress per lead
    Templates  all 13 with live Meta status and copy-for-Interakt
    Settings   dry-run switch, daily cap, send window, connection
               health, and a "Run now" button for the engine

  Underneath: migration 047 — the queue-and-drain sending engine
  with the send window, global + per-sequence daily caps, opt-out
  triggers, and retry logic, all enforced in Postgres.

HOW TO INSTALL
  1. Drag app/, components/, supabase/ into your repo root,
     replacing files. Let Netlify deploy.
  2. Supabase → SQL Editor → run:
       supabase/migrations/047_whatsapp_sequences.sql
     Safe to run twice.
  3. Set up the cron (one time): in cron-job.org (or wherever your
     other crons live) add, every 10 minutes:
       POST https://crm.migrizo.com/api/whatsapp/sequences/drain
       header  x-cron-secret: <your CRON_SECRET>
     Until the cron exists, the "Run now" button in Settings does
     the same thing by hand.

FIRST TEST (10 minutes, fully safe — dry-run is still on)
  1. WhatsApp → Sequences → New sequence.
  2. Add 2 steps: Cold 1 (sends on enrol), Cold 2 wait 4 days.
  3. Save → Activate.
  4. Enrol leads → search your own test lead → "Only enrol the
     first 1" → check the maths line → Enrol.
  5. Settings → Run now. You should see "1 sent (dry-run)".
  6. Sequences tab: your lead shows step 1/2, next send in 4 days.
  7. Nothing reached any phone. When Meta approves the templates
     and you're ready: Settings → turn dry-run OFF.

THE RULES THE ENGINE ENFORCES (in Postgres, not in the browser)
  * Send window: default 10:00–19:00 IST. Outside it, the engine
    claims nothing; anything scheduled later rolls to next opening.
  * Global daily cap: one number for ALL sends, because Meta
    rate-limits the phone number, not your sequences.
  * Per-sequence daily limit: optional, can only lower the global.
  * STOP/NO: the suppression trigger stops every enrollment for
    that number instantly. Claim re-checks at send time too.
  * A reply NEVER stops a sequence (your rule). It flags the lead
    ("replied" chip) and the thread; a human decides.
  * Edits apply going forward: each lead remembers only how many
    steps they received; the next one comes from the current list.
  * 3 consecutive send failures stop that enrollment and surface
    the error on the row.
  * Crash-safety: claims carry a 10-minute lease, rows are written
    before Interakt is called, overlapping crons skip locked rows.

DESIGN
  The reference (Sowtek unified inbox) drives the new look: pill
  sub-tabs, white cards on the grey canvas, circular quick-action
  row and label/value pairs on the contact panel, interaction-
  history list, status chips everywhere. Channel icons for email/
  social were deliberately NOT copied — dead buttons make a
  product feel worse, and this module is WhatsApp-only today.

VERIFICATION DONE BEFORE SHIPPING
  Migration 047 applied twice on PostgreSQL 16 — clean both times.
  Window clamp: all 5 boundary cases exact (03:30→10:00 same day,
    14:00 unchanged, 19:00→next 10:00, 22:45→next 10:00,
    09:59:59→10:00).
  Step save renumbers 1..N and rejects forged template ids.
  Enrol preview counts == enrol results; re-enrol is a no-op;
    suppressed and bad-phone leads excluded.
  Claim: lease prevents double-claim; global cap 2 with 3 due
    claims exactly 2; per-sequence limit 1 claims exactly 1 and
    defers the rest to tomorrow's window.
  Advance: success walks step 1→2→completed with 4-day scheduling;
    3 failures → stopped with the error recorded.
  Suppression trigger stops enrollments instantly; inbound-reply
    trigger flags has_replied and does NOT change status.
  Full drain cycle simulated with real message recording:
    provenance (sequence_step = "<seq>:<n>") feeds the per-seq
    cap query; second same-day cycle correctly claims 0.
  npx tsc --noEmit clean; next build green — /whatsapp 30.4 kB
    with /api/whatsapp/sequences/{enroll,drain} in the manifest.
